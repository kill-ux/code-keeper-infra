# Code-Keeper Infra

Infrastructure-as-code for the Code-Keeper platform. This repository contains Terragrunt/Terraform composition for provisioning shared AWS resources (foundation) and workload resources that host the microservices (api-gateway, inventory-app, billing-app), supporting services (RabbitMQ, Postgres) and the CI/CD integration points.

Key characteristics:
- Terragrunt is used to compose and orchestrate Terraform modules
- Remote state is stored in an S3 backend (generated by root.hcl)
- Staging and production environments are modeled separately under `staging/` and `production/`
- The repo includes helper scripts to import existing resources and manage ECR entries

## Repository layout

```
code-keeper-infra/
├── modules/                # reusable Terraform modules (aws/*)
├── foundation-source/      # foundation composition used by staging/production
├── workload-source/        # workload composition (ECS, ALB, services)
├── staging/                # terragrunt configs for staging (foundation + workload)
├── production/             # terragrunt configs for production
├── shared/                 # shared resources (certs, secrets modules)
├── scripts/                # operational scripts (import, state cleanups)
├── root.hcl                # shared Terragrunt root with remote state/provider generation
├── .gitlab-ci.yml          # CI pipeline for planning/applying infra
└── .env.example            # example env vars used by scripts and CI
```

## Prerequisites

- Terraform >= 1.15 and Terragrunt
- AWS CLI configured with credentials that can manage the target AWS accounts
- An S3 bucket and DynamoDB table are created automatically by the Terragrunt-generated backend (see `root.hcl`) or must be present with appropriate permissions for the pipeline user
- `jq`, `aws`, and typical shell tooling when running scripts locally

Note: CI uses the image `alpine/terragrunt:tf1.15.8` and runs non-interactively.

## Remote State and Provider

`root.hcl` generates a `backend.tf` that configures an S3 backend with an account/region-specific bucket:

- Bucket name: code-keeper-infra-tfstate-<account_id>-<region>
- Key: derived from the relative path inside the repo (`${path_relative_to_include()}/terraform.tfstate`)
- The provider configuration is generated automatically with a default AWS region (eu-west-3 in the shipped root.hcl)

This central configuration ensures environments produce isolated state files while sharing common provider settings.

## Common Terragrunt commands

From the repository root, run the Terragrunt wrapper or call Terragrunt in a working directory. Examples:

- Initialize all modules for a working dir (staging or production):

```bash
terragrunt run --all --working-dir staging init
terragrunt run --all --working-dir production init
```

- Validate and plan (recommended to run in CI):

```bash
terragrunt run --all --working-dir staging validate
terragrunt plan --working-dir staging/foundation -out=staging.foundation.tfplan
terragrunt plan --working-dir staging/workload
```

- Apply (CI runs these as manual protected jobs):

```bash
terragrunt apply --working-dir staging/foundation -auto-approve staging.foundation.tfplan
terragrunt apply --working-dir staging/workload -auto-approve
```

- Destroy (manual, use with caution):

```bash
terragrunt destroy --working-dir staging/workload -auto-approve
```

## CI / GitLab integration

The included `.gitlab-ci.yml` defines stages for `init`, `validate`, `plan`, `apply_staging`, `apply_production`, and `destroy`. Key behaviors:

- `init` and `validate` run Terragrunt across the chosen working directory
- `plan` produces plan artifacts in the pipeline and stores them as job artifacts
- `apply_staging` is a manual, protected job that consumes the staged plan
- `apply_production` requires `apply_staging` to have run successfully and is also manual and protected
- A bootstrap check is used to set a `TF_VAR_bootstrap` variable when the workload is being created for the first time

Ensure the CI runner has permissions to access the S3 backend and the target AWS account to run apply operations.

## Useful scripts

- `load-env.sh` — loads environment variables from `.env` files to ease local testing

Inspect `scripts/` before running — some import operations assume resource names and can modify Terraform state.

## Development and testing

- Use `terragrunt run --all` with `plan`/`validate` to catch errors locally before pushing
- Use the `mock_outputs` in Terragrunt dependency blocks (as used by `staging/workload/terragrunt.hcl`) to allow `plan` and `validate` to run without requiring all upstream resources during CI analysis
